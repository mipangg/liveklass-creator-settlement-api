# 과제 B — 크리에이터 정산 API

## 프로젝트 개요

본 프로젝트는 크리에이터 강의 판매 데이터를 기반으로 정산 금액을 계산하고 조회하는 백엔드 API입니다.

플랫폼에서 발생하는 판매/취소 데이터를 기반으로:

- 크리에이터별 월 정산 금액을 계산하고
- 운영자가 기간별 전체 정산 현황을 집계할 수 있도록 설계되었습니다.

특히 다음과 같은 실제 서비스 상황을 반영했습니다:

- 판매 이후 취소(환불)가 발생할 수 있음
- 정산 기준은 “결제일”과 “취소일”이 다름
- 월 단위 정산 처리 필요
- 수수료(20%)를 제외한 금액을 정산

## 실행 방법

본 프로젝트는 Docker 기반으로 실행 환경을 통일하여, 누구나 동일한 환경에서 쉽게 실행할 수 있도록 구성했습니다.

### 1. 사전 준비
- Docker 설치 필요
- Docker Compose 사용 가능 환경

### 2. 프로젝트 실행

#### 2.1 저장소 클론
```bash
git clone https://github.com/mipangg/liveklass-creator-settlement-api.git
cd liveklass-creator-settlement-api
```

#### 2.2 Docker 실행

```bash
docker-compose up --build
```

#### 2.3 실행 확인

- 서버: [http://localhost:8080](http://localhost:8080)
- DB: localhost:3306(MySQL)

### 3. 주요 환경 변수

Docker 실행 시 다음 환경 변수가 자동으로 설정됩니다:

```yaml

SPRING_DATASOURCE_PASSWORD: 1234
```
- 환경 변수는 docker-compose.yml에서 수정 가능합니다.
- 보안을 위해 실제 서비스에서는 환경 변수를 외부(.env 등)에서 관리하는 것을 권장합니다.

### 4. 로그 확인

```bash
docker-compose logs -f
```

### 5. 종료 방법

```bash
docker-compose down
```

### 6. 참고 사항

- 애플리케이션과 MySQL은 Docker Compose로 함께 실행됩니다.
- 로컬 환경 차이에 영향을 받지 않도록 컨테이너 기반으로 구성했습니다.
- 일부 기능(정산 내역 엑셀 다운로드)은 현재 미구현 상태입니다.

## 요구사항 해석 및 가정

### 핵심 해석

정산 기준 정의:

* 판매 금액 기준: `paidAt`(결제일)
* 취소 금액 기준: `canceledAt`(취소일)

즉, 같은 판매라도 서로 다른 월에 반영될 수 있습니다.

--- 

### 주요 가정

#### 1. 수수료율

- 현재는 20% 고정
- `CommissionRate` 테이블로 확장 가능하도록 설계

#### 2. 정산 월

- `YearMonth` 개념 사용
- DB에는 `DATE(yyyy-MM-01)` 형태로 저장

#### 3. 빈 정산 데이터

- 판매/취소가 없는 경우 → 0원 반환

#### 4. 정산 상태

- `PENDING → CONFIRMED → PAID`
- 현재는 상태 필드만 존재(일부 로직만 구현)

---

### 추가 고려 사항(가산점 요소)

- 잘못된 연월 요청(예: 2025-13)
- 미래 날짜 조회
- 동일 월 다수 취소 케이스
- 취소만 존재하는 월 처리 정책

#### 정산 기록 저장 전략

- 과거 월: Settlement 테이블 조회 후 없으면 생성 및 저장
- 현재 월: 실시간 계산(DB 저장 X)
- 집계 조회 시: 종료 월은 지난 달까지만 허용

## AI 활용 범위

본 프로젝트에서는 AI를 단순 코드 생성 도구가 아닌,  
**설계 검토 및 문제 해결을 위한 보조 도구**로 활용했습니다.

특히, 다음과 같은 고민 과정 속에서 AI를 활용했습니다:

---

### 1. API 설계 개선(RESTful 구조)

#### 고민
- 크리에이터별 월별 정산 조회와 정산 집계 API를 어떻게 더 RESTful하게 설계할 수 있을지 고민
- “행위 중심”이 아닌 “리소스 중심”으로 표현하는 것이 적절한지 검토

#### 활용
- API URI 구조 및 파라미터 설계에 대해 AI에게 다양한 방식 제안 요청

#### 결과
- `/settlements/monthly`, `/settlements`와 같이 리소스 기반으로 역할이 명확히 분리된 API 구조로 개선

---

### 2. 정산 로직 검증(월 경계 & 타임존 문제)

#### 고민
- 서버는 KST 기준으로 동작하지만, DB에는 UTC로 저장되는 상황에서  
  월 경계(예: 3월 1일 00:00)의 기준이 모호해질 수 있음

#### 활용
- 타임존 변환 처리 방식 및 Jackson 설정에 대해 AI와 검토
- 날짜 비교 시 발생할 수 있는 문제 케이스 확인

#### 결과
- `JacksonConfig`를 통해 시간대 보정 설정 적용
- `DateTimeUtils`를 활용하여 명시적으로 KST 기준 변환 처리
- 월 경계가 의도와 다르게 계산되는 문제를 방지

---

### 3. 네이밍 및 코드 구조 개선

#### 고민
- DTO, 서비스 메서드 이름만으로도 역할과 의도를 명확히 드러내고 싶었음
- 특히 정산 로직처럼 계산 과정이 많은 경우, 메서드 단위 책임 분리가 중요하다고 판단

#### 활용
- 메서드 네이밍, DTO 구조, 책임 분리 방식에 대해 다양한 후보를 검토

#### 결과
- “무엇을 하는지” 드러나는 네이밍으로 개선
- 단일 책임 원칙을 유지하는 구조로 리팩토링

---

### 4. 테스트 케이스 확장

#### 고민
- 제공된 샘플 데이터만으로는 모든 케이스를 검증하기 부족
- 어떤 엣지 케이스를 추가해야 할지 판단 필요

#### 활용
- 다양한 정산 시나리오(부분 환불, 월 경계, 빈 데이터 등) 아이디어 도출

#### 결과
- 아래와 같은 케이스를 추가로 고려:
    - 월 경계 취소
    - 빈 월 조회
    - 잘못된 연월 요청
    - 미래 날짜 요청

---

### 5. 샘플 데이터 자동 등록 구조 설계

#### 고민
- JSON 형식으로 제공된 샘플 데이터를 어떻게 효율적으로 관리하고, 애플리케이션 실행 시 자동으로 등록할 수 있을지 고민
- 하드코딩 방식은 가독성과 유지보수성이 떨어짐

#### 활용
- JSON 기반 데이터 로딩 방식 및 초기 데이터 삽입 전략 검토

#### 결과
- JSON 파일을 통해 샘플 데이터를 관리하도록 설계
- 애플리케이션 실행 시 자동으로 데이터를 등록하는 구조 구현
- 새로운 데이터 추가/수정 시 코드 변경 없이 JSON만 수정 가능하도록 개선

### 2. 주요 테스트 시나리오

본 프로젝트는 정산 로직의 정확성을 검증하기 위해 다음과 같은 시나리오를 테스트했습니다.

#### 1. 크리에이터 월 정산 계산
- creator-1 / 2025-03 기준
- 총 판매, 환불, 순 판매, 수수료, 정산 금액 검증

#### 2. 부분 환불 처리
- 결제 금액보다 작은 환불 금액 처리
- 순 판매 금액에 정확히 반영되는지 확인

#### 3. 월 경계 케이스
- 1월 결제 / 2월 취소
- 서로 다른 월에 반영되는지 검증 

#### 4. 빈 월 조회
- 판매/취소 데이터가 없는 경우
- 0원 반환 확인

#### 5. 현재 월 vs 과거 월 정산 처리 차이(추가)

- **케이스 설명**
    - 현재 월 정산 조회 시:
        - 판매/취소 데이터가 계속 변경될 수 있으므로
        - DB에 정산 데이터를 저장하지 않고 조회 시점 기준으로 계산만 수행
    - 과거 월 정산 조회 시:
        - 해당 크리에이터와 월의 정산 데이터가 DB에 존재하는지 확인
        - 없으면 새로 생성하여 저장(정산 스냅샷 생성)

- **추가 이유**
    - 현재 월은 데이터가 변동될 가능성이 높아 정산 값을 고정하면 안 되기 때문
    - 반면, 과거 월은 이미 정산이 완료된 데이터로 간주하여 스냅샷 형태로 보존 필요
    - 이를 통해 정산 값의 일관성과 재현 가능성을 보장

#### 6. 동일 판매에 대한 다중 취소(추가)

- **케이스 설명**
    - 하나의 판매에 대해 여러 번 부분 환불이 발생하는 경우
    - (예: 80,000 → 30,000 환불 → 추가 20,000 환불)

- **검증 포인트**
    - 누적 환불 금액이 정확히 반영되는지
    - 순 판매 금액이 정상적으로 감소하는지

- **추가 이유**
    - 실제 서비스에서 부분 환불이 여러 번 발생할 수 있음
    - 단일 취소만 고려하면 정산 오류 발생 가능

#### 7. 수수료 계산 소수점 처리(추가)

- **케이스 설명**
    - 수수료 계산 시 소수점이 발생하는 금액(예: 33,333원)

- **검증 포인트**
    - 반올림/버림 정책이 일관되게 적용되는지

- **추가 이유**
    - 금액 계산에서 소수점 처리 정책이 불명확하면 정산 오류 발생 가능

#### 8. 기간 필터 경계값(추가)

- **케이스 설명**
    - 조회 시작일과 종료일이 정확히 경계에 위치하는 경우
    - (예: 2025-03-01 00:00:00 / 2025-03-31 23:59:59)

- **검증 포인트**
    - 해당 데이터가 포함되는지 여부 확인

- **추가 이유**
    - 경계 포함/제외 기준이 불명확하면 데이터 누락 가능

#### 9. 크리에이터 데이터 분리 검증(추가)

- **케이스 설명**
    - 여러 크리에이터의 데이터가 존재하는 상황에서 특정 크리에이터 조회

- **검증 포인트**
    - 다른 크리에이터의 데이터가 포함되지 않는지 확인

- **추가 이유**
    - 필터링 누락 시 심각한 정산 오류 발생 가능

- 잘못된 연월 형식 요청
- 미래 날짜 조회
- 취소만 존재하는 경우
- 환불 요청액이 원결제 금액보다 큰 경우
